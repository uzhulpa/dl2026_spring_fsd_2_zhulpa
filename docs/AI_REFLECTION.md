# Рефлексия: опыт использования AI при выполнении задания

В ходе работы над проектом географической викторины я опиралась на генеративные инструменты не как на «автора готового решения», а как на **ускоритель** этапов проектирования, формулировки требований и чернового кода. Ниже зафиксированы **какие** инструменты использовались, **какие** запросы отправлялись (в переработанном, более точном виде), и **какой** у этого был практический эффект.

---

## 3.1. Применённые инструменты и промпты

### Инструменты

| Инструмент | Роль в работе |
|------------|----------------|
| **DeepSeek** | Раннее **проектирование**: обсуждение сценариев, структуры экранов, эндпоинтов, последовательности действий пользователя на высоком уровне. |
| **Cursor** | **Повседневная разработка** в репозитории: навигация по коду, генерация и правки фрагментов, документация (`README`, `design.md`), согласование текста с фактической реализацией. |
| **ChatGPT** | **Точечные** запросы: уточнение формул, SQL/Sequelize, схем валидации — когда нужен быстрый черновик без глубокого контекста всего проекта в одном чате. |

Ниже приведены **исходные замыслы** моих запросов и **улучшенные формулировки** — так, как их имеет смысл писать с точки зрения промпт-инжиниринга: явный контекст, формат ответа, ограничения и критерии качества.

### Промпт 1: обзор страниц и потока пользователя

**Исходная идея запроса:** описать все страницы приложения — от входа на главную до сценариев игры; для каждой страницы указать содержимое, функции и вызовы API с учётом уже согласованных эндпоинтов.

**Улучшенная формулировка:**

> Ты — аналитик фронтенда. Стек: React, REST API с префиксом `/api`.  
> **Задача:** опиши **пользовательский путь** от первого захода до ключевых сценариев (лендинг, регистрация/вход, бесконечная игра, коллекции, лидерборд, админка — если есть в ТЗ).  
> **Для каждой страницы/маршрута укажи:**  
> — назначение;  
> — основные UI-блоки;  
> — какие **действия пользователя** ведут к **каким HTTP-запросам** (метод, путь относительно `/api`);  
> — что ожидается в ответе на уровне смысла (без выдумывания полей, которых нет в списке эндпоинтов).  
> **Входные данные:** [вставить список согласованных эндпоинтов].  
> **Формат:** таблица или нумерованный список по маршрутам.

**Для чего нужен был запрос:** структурировать **навигацию и связь UI ↔ API** на этапе проектирования, чтобы потом не «додумывать» вызовы в процессе вёрстки.

**Короткий разбор формулировки:** явная **роль**, **ограничение** «не придумывать поля» и приложенный список эндпоинтов снижают галлюцинации; требование **таблицы по маршрутам** делает ответ пригодным для чек-листа при ревью.

### Промпт 2: план реализации фронтенда

**Исходная идея:** получить план внедрения фронтенда на React + JavaScript со сборщиком Vite.

**Улучшенная формулировка:**

> Нужен **пошаговый план** реализации клиентской части географической викторины.  
> **Стек:** React (JavaScript, без TypeScript), Vite, React Router, работа с картой (Leaflet или аналог — обоснуй выбор), axios/fetch для REST.  
> **Ограничения:** JWT в заголовке `Authorization: Bearer`, базовый URL API из переменной окружения.  
> **Выход:** фазы (инициализация проекта, маршруты, контекст авторизации, страницы игры/коллекций/админки, обработка ошибок), **порядок** задач с учётом зависимостей, **риски** (CORS, токен, 401).  
> Без полного кода — только план и критерии готовности этапа.

**Для чего:** разбить большую задачу на **последовательные** этапы и не упустить инфраструктурные вещи (env, роутинг, защищённые маршруты).

**Разбор:** добавлены **явный стек**, **ограничения безопасности** и запрет «вылить весь код» — иначе модель часто выдаёт шаблонный проект вместо управляемого плана.

### Промпт 3: формулы начисления баллов

**Исходная идея:** предложить формулы с учётом точности и скорости; для `point_with_radius` — максимум за попадание в круг; для `point` — максимум за точку; вне зоны — штраф по расстоянию; время нормировать по сложности 1–10.

**Улучшенная формулировка:**

> Спроектируй **модель начисления очков** за один ответ в географической викторине.  
> **Входы:** координаты клика и эталона; `question_type` ∈ {`point`, `point_with_radius`}; для радиуса — `radius_meters`; `response_time_ms`; `difficulty` ∈ [1, 10].  
> **Требования:**  
> 1) **Точность:** для `point_with_radius` попадание **внутрь** круга (расстояние ≤ радиуса) даёт **максимальный** вклад точности; для `point` — максимум при нулевом (или минимальном) отклонении; при промахе вклад убывает с **эффективным** расстоянием (опиши, как считать расстояние на сфере).  
> 2) **Скорость:** задай **допустимое время** как функцию от `difficulty` (например, линейная интерполяция между T_min и T_max секунд); если время ответа ≥ допустимого — бонус за скорость = 0; если меньше — бонус растёт при уменьшении времени (предложи конкретную монотонную формулу).  
> 3) **Итог:** как объединить вклад точности и скорости в **одно** число очков (сумма, произведение, нормализация) и нужен ли **потолок** на один ответ.  
> **Выход:** математические формулы + словесное обоснование + пример численно для 2–3 ситуаций.

**Для чего:** зафиксировать **игровой баланс** до кодирования и согласовать его с реализацией на сервере.

**Разбор:** разделение на **пункты 1–3**, явные **переменные** и просьба **не брать магические числа из примера пользователя** как догму — помогает получить переносимую спецификацию; примеры чисел в конце проверяют понятность.

### Промпт 4: выборка лидеров infinite-режима (Sequelize)

**Исходная идея:** функция `getInfiniteLeaders(limit, offset)` — для каждого `user_id` сумма `score_awarded` по `answer_attempts` с `game_mode = 'infinite'`, с пагинацией.

**Улучшенная формулировка:**

> Нужна реализация на **Node.js + Sequelize** для PostgreSQL.  
> **Задача:** метод `async getInfiniteLeaders(limit, offset)` возвращает список пользователей с **суммой** поля `score_awarded` по таблице `answer_attempts`, отфильтрованной по `game_mode = 'infinite'`, с **группировкой** по `user_id`, **сортировкой** по убыванию суммы, **LIMIT** и **OFFSET**.  
> В выборке должны участвовать `users` (хотя бы `id`, `username`).  
> **Предпочтение:** один запрос через `sequelize.query` с raw SQL **или** эквивалент через `findAll` + `attributes` + `include` — выбери читаемый вариант.  
> **Вход:** при необходимости приложена схема моделей Sequelize.

**Для чего:** быстро получить **корректный** шаблон агрегации без ручного перебора синтаксиса Sequelize.

**Разбор:** указание **СУБД**, **имён таблиц/полей**, **ожидаемых колонок результата** и допустимости **raw SQL** снижает риск несовпадения с реальной схемой.

### Промпт 5: исправление лидерборда по коллекции

**Исходная идея:** для коллекции считать «суммарные» очки пользователя по сессиям; при нескольких сессиях одного пользователя брать **лучшую** (максимальный `total_score` сессии), вернуть `id`, `username`, баллы.

**Улучшенная формулировка:**

> Исправь логику **рейтинга по коллекции** `collectionId`.  
> **Бизнес-правило:** для каждого пользователя нужно взять **максимальное** значение `total_score` среди записей `game_sessions`, где `collection_id = :collectionId` и сессия **связана** с попытками ответа в режиме `collection` (или опиши, как избежать «пустых» сессий без попыток).  
> **Результат:** строки с `user_id`, `username`, `total_score` (лучший забег), сортировка по убыванию баллов, пагинация `limit`/`offset`.  
> **Контекст:** [фрагмент текущей реализации SQL / модели].  
> Укажи возможные **краевые случаи** (нет сессий, дубликаты пользователей в выборке).

**Для чего:** согласовать **метрику** лидерборда с продуктовым смыслом («лучший проход» vs «сумма всех проходов») и избежать ошибки в JOIN.

**Разбор:** изначально формулировка смешивала «сумму попыток» и «сумму по сессиям»; улучшенный промпт **фиксирует одну метрику** (max по сессиям) и просит **явно** связать с `answer_attempts`, что ближе к проверке целостности данных.

### Промпт 6: Zod-схема для админ-вопроса

**Исходная идея:** заполнить `adminQuestionSchema` по полям физической модели БД (типы, NOT NULL, CHECK, enum статуса).

**Улучшенная формулировка:**

> Напиши **схему Zod** для тела запроса создания/обновления вопроса (админка), согласованную с полями:  
> — `title`: string, max 200, обязательное;  
> — `description`: string, optional/nullable;  
> — `image_url`: string (URL), optional/nullable;  
> — `correct_longitude` / `correct_latitude`: числа в диапазонах [-180, 180] и [-90, 90];  
> — `question_type`: enum `point` | `point_with_radius`;  
> — `radius_meters`: positive integer, **обязательно** если `question_type === 'point_with_radius'`, иначе optional/null;  
> — `difficulty`: integer 1–10;  
> — `status`: enum `moderation` | `active` | `inactive`.  
> Используй `.refine()` или `superRefine` для условного радиуса.  
> **Выход:** только код схемы + кратко, какие поля optional при PATCH.

**Для чего:** получить **валидатор**, повторяющий ограничения БД, и не пропустить **условную** обязательность `radius_meters`.

**Разбор:** в сыром запросе не было явного `question_type`; в улучшенной версии добавлены **кросс-полевые** правила — без них Zod легко оказывается согласован с колонками, но **несогласован** с игровой логикой.

## 3.2. Анализ эффективности

### Где AI оказался наиболее полезен

**Проектирование и декомпозиция.** На этапе обсуждения в **DeepSeek** и при структурировании сценариев в **Cursor** модель хорошо справлялась с **разбиением** задачи на страницы, маршруты и списки вызовов API. Это **ускорило** переход от общей идеи к **проверяемому** чек-листу: что должно быть на экране и что дергается на бэкенде.

**Черновики формул и SQL.** Запросы про **скоринг** и про **агрегации** для лидербордов дали **рабочую основу** для обсуждения: даже когда формула позже упрощалась или менялась под константы в коде, **рамка** (точность + скорость + ограничение сверху) оказалась полезной.

**Рутинные фрагменты кода.** Валидация Zod, шаблоны Sequelize-запросов, мелкие правки под стиль проекта — здесь **Cursor** и **ChatGPT** экономили время на **поиске синтаксиса** и низкоуровневых примеров.

### Где ответы требовали серьёзной корректировки или были неверны

**Расхождение с уже принятыми решениями в коде.** AI мог предложить **другую** метрику для коллекционного лидерборда (например, сумму попыток вместо max по сессии) или **другой** способ нормализации времени. **Обнаружение:** сверка с `LeaderboardService` и с продуктовым смыслом («лучший результат прохождения»). Итог — ручная правка SQL и тест на глаз по данным.

**Неполный контекст домена.** В ответах про страницы иногда появлялись **лишние** сущности или поля API, если в промпт **не** был вложен актуальный список эндпоинтов. **Обнаружение:** сопоставление с `ApiRouter` и контроллерами.

**Формулы без привязки к стеку.** Предложенные коэффициенты для скорости/точности нередко требовали **подгонки** под существующие `constants.js` и проверки на краевых значениях (очень большая дистанция, время ровно на границе допустимого).

### Примеры по пунктам задания

- **Где AI помог ускорить разработку:** быстрый каркас **плана фронтенда**, черновики **SQL** для лидеров, **Zod**-схемы после уточнения полей — меньше времени на поиск документации по синтаксису.

- **Где AI ошибся и как я это обнаружила:** несоответствие **бизнес-правил** лидерборда по коллекции фактической реализации или здравому смыслу «один пользователь — одна строка с лучшим счётом»; проверка **чтением кода** и **прогоном** запроса на тестовых данных.

- **Когда сознательно отказалась от предложения AI:** если предлагалось **усложнить** архитектуру (лишние слои, другой стек) без выгоды для учебного проекта; если ответ **противоречил** уже зафиксированным эндпоинтам или модели данных — сохраняла **контракт** репозитория, а не «красивый» абстрактный вариант.

## 3.3. Выводы и рекомендации

**Вывод 1.** AI наиболее эффективен, когда запрос снабжён **контекстом** (стек, ограничения, фрагмент кода, список API) и **форматом ответа** (таблица, план, только формулы). Без этого экономия времени на черновике съедается на **исправление галлюцинаций**.

**Вывод 2.** Для **критичных** вещей — деньги, безопасность, **единая метрика** рейтинга — ответ AI нужно считать **гипотезой**, проверяемой **кодом**, тестами или хотя бы ручной проверкой на данных. Полезно явно просить в промпте **краевые случаи** и **противоречия**.

**Вывод 3.** Разные инструменты лучше **разделять по задаче**: «широкое» проектирование и мозговой шторм — в одном типе чата; **правки в репозитории** — в IDE с доступом к файлам (**Cursor**), чтобы ответ опирался на **актуальные** пути и имена.

**Как планирую использовать AI дальше:** как **помощника** при декомпозиции задач, написании тестов и документации, рефакторинге с явными инвариантами — но не как источник **непроверенных** требований к продукту.

**Коллегам, кто начинает:** формулируйте **цель**, **входные данные**, **ограничения** и **желаемый формат** ответа; **всегда** верифицируйте сгенерированный код запуском, линтером или ревью; не смешивайте в одном запросе **пять несвязанных** вопросов — качество падает; помните, что модель **уверенно** может ошибаться — уверенность не равна правоте.
